## 1. 効いた二つ

同一のテストデータ・判定基準・閾値探索範囲（15 値）で測定。

### 推論集約（WBF）— 新データも再学習も不要

NMS は重なりクラスタの最高スコア箱以外を捨てるため、一つのモデル／ビューだけが
見つけた真陽性が失われる。WBF は座標を加重平均して確信度を累積するので残る。
**recall 優先の要件に対して、この非対称性が正しい向き。**

| ブレース | 精度下限 | 基線 | 2 モデル | 2 モデル + TTA |
|---|---|---:|---:|---:|
| | P>=0.60 | 0.458 | 0.518 | **0.602** |
| | P>=0.50 | 0.590 | 0.627 | **0.663** |
| | P>=0.40 | 0.627 | **0.711** | 0.699 |

柱脚（2 モデル）: P>=0.40 で 0.611（基線 0.556）、P>=0.30 で 0.667（0.597）。**未達。**

単一モデル + 水平反転 TTA だけでもブレース P>=0.50 で 0.651。計算量はどちらも
2 倍だが、**単一モデルなら重みが一つで済む**ので運用上はこちらが安い。
`tta_wbf_eval.py` / `ensemble_wbf_eval.py`。

### BRL（疎な注釈のための損失）— 追加コストなし

RF-DETR の `loss_labels` では未マッチ query が `neg_weights = prob ** gamma` を
負う。**確信度が高いほど強く背景へ押される。** ラベルが完全なら正しいが、
不完全なら最悪——モデルが最も確信している query こそ未注釈の損傷であり、
そこに最大の負の勾配がかかる。**これが「真の損傷が誤検出より低いスコアを持つ」
の生成機序。**

`brl_patch.py --brl-threshold 0.35 --brl-mode ignore` で、確信度の高い未マッチ
query の背景圧をゼロにする。

| ブレース 精度下限 | 基線 | BRL 単一モデル |
|---|---:|---:|
| P>=0.55 | 0.542 | **0.590** |
| P>=0.50 | 0.590 | **0.639** |
| P>=0.45 | 0.614 | **0.663** |
| P>=0.40 | 0.627 | **0.675** |

六点すべて正、幅 0.048 前後で安定。**柱脚には効かない。**

**論文原版の `flip`（正例として学習）は採ってはならない**——両カテゴリとも
PR 曲線が P>=0.30 にすら届かない。本モデルは未見の健全部材に 95.7% 発火するので、
その誤検出を正例と断定すれば誤検出が増えるだけである。

## 2. 評価プロトコルの誤り三件（本日発見・修正済み）

**この日の前半の数値はこれらにより実験側に不利に歪んでいた。** 以後は
`select_and_score_recall_first.py` を通すこと。

1. **epoch を `val/mAP_50` で選んでいた。** config は `primary_metric: test/recall`
   と明記し、「自動の checkpoint_best_total.pth は mAP で選ばれるので使うな」と
   警告までしている。両者の選ぶ epoch は実際に異なる。
2. **閾値グリッドが 5 値だった**（0.20-0.40）。交付基線は 15 値（0.05-0.50）。
   低閾値域が探索されず recall が人為的に抑えられていた。修正で ctrl80 が
   0.389 → 0.458。
3. **medium に 30 epoch を適用した。** RFDETRSmall のピークが ep15 なのを
   一般化したが、柱脚の medium は ep30 時点で val/recall が単調上昇中（未収束）。

### データ汚染バグ（修正済み）

`os.link` でハードリンク複製したデータセットのラベルをその場で書き換えると、
**inode を共有するため元データも壊れる**。relabel → neg ビュー → 基礎データセットと
三層に伝播し、凍結 lock の `train.boxes_by_grade.D` が 29 → 33 になった。
paired から再構築し `freeze --check` 一致を確認済み。書き込み前に `unlink()` する。

## 3. 最重要の発見：注釈が不完全

`audit_annotation_completeness.py` による全数監査。**注釈済みの学習画像**に
損傷インベントリを取り、GT 箱と突き合わせた。

| | 監査画像 | GT 箱 | 箱で覆われていない領域 | 未注釈損傷を含む画像 |
|---|---:|---:|---:|---:|
| 柱脚 | 179 | 248 | **168 (49%)** | **87 / 179 (49%)** |
| ブレース | 235 | 394 | 154 (50%) | 86 / 235 (37%) |

判定器には既知の過読傾向がある（客先が空ラベルとした画像の 69% に損傷を見る）
ため、単純な比率では規約と漏れを分離できない。**種類別の内部比較**で分ける：

| 損傷種別 | GT 箱あり | 箱なし | 漏れ率 | 判読 |
|---|---:|---:|---:|---|
| **剥落** | 17 | 8 | **32%** | 標注不一致 |
| **ひび割れ** | 8 | 7 | **47%** | 標注不一致 |
| 腐蝕/錆 | 2 | 14 | 88% | 規約（客先は表面錆を等級付けしない） |

**剥落とひび割れは客先が明確に等級付けする種別**なのに、同種の 3〜5 割が箱を
持たない。規約なら「付ける／付けない」のどちらかであって、半分だけ付けることは
ない。同じ損傷が画像により正例／背景と教えられれば、検出器はその種別に
中間的なスコアしか与えられない。**これが柱脚の見逃しの主要因と考えられる。**

二カテゴリで問題が違う：

| | 剥落/ひび割れの漏れ | 未注釈領域の主な種別 |
|---|---:|---|
| 柱脚 | 48 / 179 (**27%**) | 腐蝕 82、剥落 22、ひび割れ 35 |
| ブレース | 11 / 235 (**5%**) | 腐蝕 43、**座屈 39**、**破断 36**、変形 10 |

**ブレースにラベルノイズはほぼ無い。** 未注釈領域の 55% は座屈・破断・変形——
部材レベルの幾何状態で、客先もこれらを箱にしていない。ブレースの困難は
**注釈体系そのもの**にある：「部材全体が変形している」を局所の箱で表現しようと
している。

## 4. 前提の訂正：交付四カテゴリとデータ量は同じ

`data_split.json` の実数は各 **train 242 / valid 28 / test 31 枚**。
文書が繰り返す「605-966 枚」は誤り。ブレース 235 / 柱脚 179 とほぼ同量である。

差は二点：**test が 31 枚 対 58/45 枚**（小さい test は選択バイアスが強く数字が
高く出る）、および**交付四種は全て「単一部材のひび割れ」**（各 config の note に
明記）。新二種は一つの等級ラベルに複数材質・複数形態が混在する。

**データ量の問題ではなく、課題の難易度が違う。**

## 5. やってはいけないこと（本日測定済み）

### 訓練側の調整（五系統すべて基線以下）

解像度 896、RFDETRSmall、正則化（drop_path 0.08 / 0.25）、統合事前学習。
正則化が小値でも大値でも効かないのはラベルノイズ仮説と整合する——正則化が
対処するのは「真のパターンへの過学習」であって「矛盾ラベルへの過学習」ではない。

### 合成データ（四通りすべて負）

* **S1（損傷除去）**: 鉄骨では損傷を消さず**部材を作り替える**。柱脚 45%、
  ブレース半数以上。しかも QC ゲートは全て合格と判定していた（「損傷が消えたか」
  しか見ていないため）。`check_geometry_preserved.py` で検出可能にした。
* **copy-paste**: ブレース −0.120。柱脚は少量で +0.014 だが**増量すると −0.125**。
* **対称版・生成健全シーン**: いずれも負。

判断基準：**「表面を直せば済む損傷」は生成可能、「部材を取り替えるしかない損傷」は
不可**。部材の種類ではなく損傷の性質で決まる。

### 領域レベルの判別を箱レベルに転用すること（三度失敗）

1. 凍結 DINOv2 + ロジスティック回帰は健全／損傷 crop を AUC 0.924 / 0.857、
   recall 0.951 / 0.921 で分離する。しかし検出器の候補箱に適用すると
   precision 0.082、best F1 が 0.561 → 0.150。
2. 負例を「検出器自身の誤検出」に替えても 0.141。**真の検出箱と誤検出箱が
   特徴空間で分離不能**だからで、識別ではなく**定位の曖昧性**の問題。
3. Gemini の補注釈は −0.097。判定器の箱は人手 GT との IoU 中央値 0.354-0.454。

VLM 全般の限界と一致：Gemini 2.5 Pro の RF100-VL ゼロショット mAP50:95 は 13.3。
**「あるか」は判定できるが、人手水準の箱は出せない。**
