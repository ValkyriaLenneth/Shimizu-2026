## 1. 壁类结果整合与可视化

### 1.1 背景

客户在上次讨论中提出的核心要求很明确：

- 拍了多少张照片，确认画面里最好还是多少张照片；
- 不希望因为系统内部同时参考多个模型，就把结果数量翻倍；
- 但如果系统确实拿不准，也不能强行只给一个答案。

这次我们就是围绕这个要求做了展示方式的调整。

### 1.2 本次改动后的展示方式

现在壁类照片的展示逻辑是：

- **同一张照片，只保留一条照片记录**
- 如果 `RC壁` 与 `内壁` 两个模型给出的等级一致：
  - 只显示一个结果，避免重复
- 如果两个模型给出的等级不一致：
  - 在同一张照片内并列显示两个候补，供确认人员参考

这样做的意义是：

- 保证照片数量和结果数量基本一致，降低核对负担
- 把系统的不确定性明确展示出来，而不是在后台悄悄替用户做判断
- 为后续结合图纸、位置关系进行人工确认保留空间

## 2. 自动识别后的流程兜底

### 2.1 为什么要加这一步

自动识别模型的作用，是先判断照片大致属于 `天井 / 壁类 / RC柱` 哪一类，再把图片送到对应的下游判定模型。

这个方向本身是对的，因为它能减少无关误检，也能减少使用者手动选模型的负担。但只要自动识别不是 100%，就会存在一个现实问题：

- 一旦前一步把类别送错，后面的正确模型可能根本没有被调用
- 这样即使下游判定模型本身有能力识别，也没有出场机会

所以我们本周加的“兜底”并不是替代自动识别，而是在系统觉得“这里可能有问题”的时候，再自动复查一次。

### 2.2 兜底策略用大白话解释

这套机制可以简单理解为：

- **正常情况下**，系统还是按自动识别结果走，不增加额外负担
- **只有系统自己也觉得可疑的时候**，才补跑另一侧模型做复查

触发复查的典型场景包括：

- 识别到的区域很奇怪，看起来不像它被分到的那一类
- 主模型几乎没有检出，像是“应该有东西，但没找到”
- 同一位置出现了容易混淆的构件关系，比如墙和柱贴得很近
- 自动识别整体信心偏低，或者几乎没有给出可用结果

换句话说，这不是“所有图片都再跑一遍”，而是“**只对可疑图片做二次确认**”。

### 2.3 这一步带来的实际改善

在 80 张抽样图片上的结果如下：

- 主分支漏检：`18 -> 14`
- 其中由自动识别误分造成的漏检：`6 -> 2`
- 判定等级正确数：`71 -> 74`
- 基本没有带来额外主分支误检

如果只看最受益的 `RC柱` 类别，改善更明显：

- `RC柱` 的自动识别漏掉张数：`5 -> 2`
- `RC柱` 主分支漏检：`8 -> 5`

这说明这套机制已经能补回一部分“前一步送错模型，后一步没机会判断”的损失。

### 2.4 已确认改善的典型样例

本次抽样中，以下 4 张图是已经确认被兜底机制救回的代表案例：

| 图片 | 类别 | 改善前 | 改善后 |
|---|---|---|---|
| `3-C-00039.jpg` | RC壁 | 漏检 1 处，等级未对上 | 成功补回，等级对上 |
| `d-173.jpg` | RC柱 | 漏检 2 处中的 1 处，且等级未对上 | 补回 1 处，并修正等级 |
| `d-40044.JPG` | RC柱 | 漏检 1 处 | 成功补回 |
| `4-C-00022.jpg` | RC柱 | 漏检 1 处 | 成功补回 |

这里建议在正式汇报材料中放“改善前 / 改善后”对比图，重点突出：

- 自动识别原本把它分错到了哪里
- 兜底复查后为什么又把正确候补找了回来
- 最终客户看到的结果有没有变得更合理

### 2.5 这一项对客户的意义

这一步的价值不在于把系统变成“完全不会错”，而在于：

- 当自动识别偶尔失误时，系统不会立刻失去补救机会
- 特别是 `RC柱` 这类容易和墙混淆的场景，可靠性会更高
- 这能减少“前面一步失误，后面整条链路都失效”的风险

## 3. 数据增强训练的结论

### 3.1 为什么要继续做数据增强

数据增强可以理解为：在不改变原始业务标签的前提下，让训练阶段看到更多“拍摄角度不同、范围不同、局部遮挡不同、损伤表现不同”的版本。

做这件事的原因很直接：

- 现场照片条件复杂
- 同一类构件在不同建筑、不同角度下差异很大
- 我们希望模型学到的是“构件本身的特征”，而不是少量固定拍法

### 3.2 本周的结论

本周我们继续沿着数据增强路线做了多轮训练比较，结论有两个：

1. **数据增强这条路线本身是有效的**
2. **本周已经把自动识别模型进一步提升到了新的可用水平**

当前建议继续作为主基线使用的模型，在独立测试集上的结果是：

- Precision: `0.863`
- Recall: `0.850`
- mAP50: `0.888`
- mAP50-95: `0.775`

如果和上周用于汇报的版本相比，当前版本已经更进一步：

- Precision: `0.843 -> 0.863`
- Recall: `0.841 -> 0.850`
- mAP50: `0.888 -> 0.888`（基本持平）

如果和更早期的清洗后基础版本相比，提升则更加明显：

- Precision: `0.699 -> 0.863`
- Recall: `0.673 -> 0.850`
- mAP50: `0.721 -> 0.888`

这说明前一阶段的数据整理、训练调参和增强策略整体上是有效的。

## 4. 合成数据生成流程

### 4.1 我们为什么要做合成数据

合成数据不是为了替代真实数据，而是为了补足真实数据里相对稀缺、但业务上很重要的场景,并增加数据的多样性。

当前最需要补的，主要是这些难例：

- `RC柱` 和 `壁类` 很接近的场景
- 只拍到局部、边界不完整的场景
- 损伤明显，但构件类别容易混淆的场景

这些情况在真实数据里往往数量不多，但恰恰最容易影响自动识别和后续模型路由。

### 4.2 为什么采用“参考图 -> 生成提示 -> 生成图 -> 同步标注”的流程

我们这次不是直接让模型凭空生成图片，而是设计成四步：

1. 从真实照片中随机抽取参考图
2. 先根据参考图生成更具体、更有变化的文字描述
3. 再用这些描述去生成新图片
4. 最后对新图片同步生成标注

这样设计有两个目的：

- **尽量让生成结果靠近真实现场照片的风格**
- **尽量保证生成的数据能直接进入训练，而不是只停留在“看起来像”**

### 4.3 本周已经完成的规模

本周主批次的生成结果为：

- 计划生成：`1200` 张
- 成功标注：`1199` 张

分类分布如下：

- 天井：`300`
- 内壁：`300`
- RC壁：`299`
- RC柱：`300`

### 4.4 肉眼观察下的结果

这部分需要实话实说：

- 生成图片的观感已经明显比最初版本更好
- 和原始照片的风格更接近
- 场景构图、损伤表现、表面纹理都更像现场图
- 作为后续继续筛选 hard case 的素材库，这批数据已经有使用价值

也就是说，**图像质量不是这次的主要问题**。

## 5. 合成数据加入训练后的结果

### 5.1 结果概览

这部分也需要实话实说。

我们尝试了三类训练方式：

1. 真实数据 + 合成数据混合训练
2. 在已有较好模型基础上继续用合成数据强化训练
3. 只用合成数据训练，再回到真实测试集验证

结果都没有稳定超过当前真实数据基线。

最接近可用的一次混合训练结果为：

- Precision: `0.8750`
- Recall: `0.8461`
- mAP50: `0.8816`
- mAP50-95: `0.7684`

和当前基线相比：

- Precision 略有上升：`+0.0120`
- Recall 略有下降：`-0.0039`
- mAP50 下降：`-0.0064`
- mAP50-95 下降：`-0.0066`

如果只看一个指标，这个结果不是完全不能用；但从整体业务效果看，它**没有形成明确的正向增益**。

进一步把合成数据比例拉高，或者只用合成数据训练后，结果反而更差。比如 synthetic-only 实验中，best recall 只有 `0.8253`，明显低于当前基线的 `0.850`。

### 5.2 我们目前的判断

目前最合理的判断是：

- 合成数据已经能做出“看起来不错”的图片
- 但这些图片还没有稳定转化为真实测试集上的识别收益

也就是说，当前阶段不能说“合成数据训练成功了”，只能说“**合成数据生成流程已经跑通，但训练价值还需要继续筛选验证**”。

从目前的实验结果看，训练收益没有出来，主要可能有四个原因：

1. **生成图和真实现场图仍然有分布差异**
   - 虽然肉眼看起来已经比较像，但在模型真正敏感的地方，仍可能存在光照层次、材质纹理、压缩噪声、模糊和遮挡等差异。
   - 这会让模型学到一部分“生成图风格”，但不一定能直接迁移到真实照片。

2. **合成标注仍可能带有噪声**
   - 这次流程是“自动生成图片，再自动生成标注”，效率很高，但并不是完全人工校验。
   - 对自动识别任务来说，框偏大偏小、类别边界不稳定、多构件互相干扰，都会直接影响训练效果。

3. **当前生成方向还没有完全打中真实难例**
   - 本周生成出的图片已经更自然、更多样，但扩展的更多是“合理样本空间”，不一定正好覆盖真实测试集中最难的误判边界。
   - 而当前系统最难的问题，主要还是墙和柱贴得很近、只拍到局部、构件边界不清、视觉上很像另一类这些场景。

4. **这个任务对“类别是否送对”非常敏感**
   - 自动识别模型不是普通检测模型，这里不是“框大概对就可以”，而是类别要尽量送对，否则就会进入错误的下游判定模型。
   - 所以哪怕合成数据让框的位置能力稍有提高，只要没有明显改善“送到正确模型”的能力，业务上就不算真正提升。
